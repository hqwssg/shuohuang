# 项目权限管理与分配建议

## 当前采集范围权限设置

已按《肃宁组织构架》建立可编辑的部门树。文档中的部门职责来自初步调研，后续可在部门管理中调整或导入正式架构，程序不根据部门名称判断权限。

```text
国能朔黄铁路发展有限责任公司
├─ 原平分公司
├─ 肃宁分公司
│  ├─ 运输生产部
│  │  ├─ 车务工队、工务工队、电务工队、综合工队
│  │  └─ 供电工队
│  │     └─ 肃北、灵寿、定西、安国、沧州西、行别营、黄骅港前、
│  │        黄骅港口、黄骅港南、北港供电工队、神港电力作业组
│  ├─ 综合办公室
│  ├─ 技术部
│  └─ 保障部
└─ 机辆分公司
   ├─ 公司机关
   ├─ 电力运用管理中心（运管中心）
   ├─ 机车检修车间
   ├─ 设备车间
   └─ 列检作业单元
```

| 数据范围 | 原业务表，表名不变 | 当前处理 |
| --- | --- | --- |
| 电力站点、区间 | `emission_station_interval` | 保留已有站点；公司归属由管理员确认和分配，不猜测边界 |
| 化石燃料 | `emission_fossil_fuel_collection_scope` | 原平、肃宁、机辆各一个公司范围；肃宁工务工队默认可维护本公司范围 |
| 外购热能 | `emission_purchased_heat_collection_scope` | 原平、肃宁、机辆各一个公司范围；肃宁保障部默认可维护本公司范围 |

已落地的电力授权示例：部门 `定州西供电工队`（当前部门 ID 3051）归属肃宁分公司，可维护 `定州西站`、`定定区间`、`定州东站` 三个电表区间。该示例只作为初始配置，其他站点仍由公司级管理员在页面中确认分公司后分配，避免根据名称猜测管理边界。

实际给人员使用时，在用户管理中将用户部门设为 `定州西供电工队`，角色设为 `供电采集员`。该角色仅提供采集点维护功能，具体可操作范围仍由三个区间授权决定；未授权区间会返回 403，并在界面给出无权限反馈。

入口：**系统管理 → 权限与菜单 → 采集范围分配**，也可打开 `/carbon/scopes`。

1. 公司级管理员为站点、区间或采集范围选择所属分公司。
2. 公司级管理员或该分公司的地区管理员选择负责部门、工队，设置“只读”或“维护”。地区管理员账号须归属分公司部门，不能转移公司归属或跨公司授权。
3. 用户加入对应部门或工队，并分配相应功能角色。工队继承上级业务部门的范围授权，但不会仅因属于分公司就自动获得全部采集点。
4. “维护”还需要角色具有对应操作权限；只有数据范围授权不能绕过按钮、接口的功能权限。
5. 未授权范围默认不可访问。更换公司归属时旧部门授权清除，必须重新选择新公司的部门。

公司归属与部门范围授权分别存储在 `sys_carbon_scope_owner`、`sys_carbon_dept_scope`，分公司名单存储在 `sys_carbon_company`，均含创建人、更新人及时间字段。部门与分类可在数据库维护，不将公司名称或区间名单写入业务判断代码。

接口同时校验当前节点和请求中的新所属范围、父表、集中器。采集树和列表过滤未授权范围；核算树过滤未授权采集点，核算树删除、移动、挂载校验相关子树。历史小计包含未授权采集点时不直接展示，避免以总量泄露其他范围数据。授权变更纳入统一操作日志，返回变更前后详情。

增量初始化文件：`sql/carbon_collection_scope_permissions.sql`。本次未修改原始 `schema.sql`，未重建或删除原有站点。

本地核验：`mvnd test -Dtest=CollectionScopeServiceTest`（在 `tpfhs-9/backend` 下执行）。前端与接口联调脚本为 `tools/test-collection-scopes.cjs`；需先安装测试依赖 `npm install --prefix .runtime/browser-check --no-save --package-lock=false playwright`，再执行 `node tools/test-collection-scopes.cjs`。脚本仅访问本地主机，临时创建并清理测试站点，不改动正式区间的公司归属。

## 一、基本模型

建议采用“用户 + 部门 + 角色 + 权限 + 数据范围”的方式管理权限。

| 对象 | 主要作用 |
| --- | --- |
| 用户 | 实际登录和操作系统的人员 |
| 部门 | 确定用户所属组织及可查看的数据范围 |
| 角色 | 定义用户可以使用哪些功能 |
| 权限 | 控制菜单、按钮和后端接口是否可用 |
| 数据范围 | 控制用户能够查看和修改哪些部门的数据 |

简单理解：**角色决定“能做什么”，部门决定“能看哪些数据”。**

## 二、权限分类

建议将权限分为三层：

1. **菜单权限**：是否显示碳核算、参数设置、大屏、日志、系统管理等菜单。
2. **操作权限**：是否允许新增、修改、删除、导入、导出、审核、发布等操作。
3. **数据权限**：只能查看本人、本部门、本部门及下级部门，或全部数据。

后端接口必须校验操作权限，不能只依赖前端隐藏按钮。

## 三、按角色分配

可设置以下基础角色：

| 角色 | 建议权限 |
| --- | --- |
| 超级管理员 | 全部功能和全部数据，仅限少数运维人员 |
| 系统管理员 | 用户、部门、角色、菜单、参数和日志管理 |
| 碳核算管理员 | 模型、核算参数、数据录入、计算、报告和大屏管理 |
| 部门负责人 | 查看和审核本部门及下级部门数据 |
| 数据录入员 | 录入、修改本人或本部门数据，不允许审核和删除关键数据 |
| 查看人员 | 只读查看报表、大屏和授权范围内的数据 |
| 审计人员 | 只读查看业务数据、操作日志和登录日志 |

一个用户可以拥有多个角色，最终权限取角色权限的并集。涉及删除、审批、发布等敏感操作时，建议单独授权。

## 四、按部门分配

部门主要用于限制数据范围，可按组织结构建立树形关系，例如：

```text
公司
├─ 生产部门
├─ 运输部门
├─ 能源管理部门
└─ 信息化部门
```

角色可配置以下数据范围：

- 仅本人数据
- 本部门数据
- 本部门及下级部门数据
- 指定部门数据
- 全部数据

例如，“生产部门数据录入员”拥有数据录入权限，但只能维护生产部门的数据；“公司审计人员”可以查看全部部门日志，但不能修改业务数据。

## 五、推荐分配流程

1. 先建立部门及上下级关系。
2. 按岗位职责建立角色，不直接为每个用户逐项配置权限。
3. 为角色分配菜单、按钮和接口权限。
4. 为角色设置数据范围。
5. 将用户加入部门，并分配一个或多个角色。
6. 使用普通账号验证页面、按钮、接口和数据范围。
7. 记录角色授权、权限变更和重要操作日志。

## 六、管理原则

- 默认不授权，只开放完成工作所需的最小权限。
- 普通业务人员不分配用户、角色和菜单管理权限。
- 新增、删除、审批、发布、导出应使用不同权限标识。
- 角色名称应体现职责，避免使用“角色1”“临时角色”等模糊名称。
- 用户调岗或离职后，应及时调整部门、角色和账号状态。
- 权限变更必须记录操作人、变更内容、时间和结果，便于审计追踪。
- 定期检查超级管理员、长期未登录账号和重复角色。

## 七、权限示例

以“碳排放数据录入”为例：

| 权限标识 | 作用 |
| --- | --- |
| `carbon:data:list` | 查询数据列表 |
| `carbon:data:add` | 新增数据 |
| `carbon:data:edit` | 修改数据 |
| `carbon:data:remove` | 删除数据 |
| `carbon:data:import` | 导入数据 |
| `carbon:data:export` | 导出数据 |
| `carbon:data:audit` | 审核数据 |

前端按钮、后端接口和数据库菜单权限应使用同一个权限标识，避免出现页面可见但接口无权访问，或页面隐藏但接口仍可调用的情况。
